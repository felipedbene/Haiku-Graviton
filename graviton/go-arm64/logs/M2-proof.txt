## KEY FINDING: a netpoller-adjacent errno bug that broke ALL non-blocking I/O
================================================================================

The FIRST on-hardware run failed every network operation — and the failure
mode was itself the diagnosis.

### (a) httpsget — BEFORE the fix
    ca-found: /system/data/ssl/CARootCertificates.pem (225076 bytes, dir=false)
    ca-found: /system/data/ssl/certs (0 bytes, dir=true)
    GET https://checkip.amazonaws.com -> ERROR after 1.975ms: Get "https://checkip.amazonaws.com": dial tcp: lookup checkip.amazonaws.com on 10.0.0.2:53: read udp 10.0.10.160:51705->10.0.0.2:53: read: operation would block
    GET https://sources.debene.dev/... -> ERROR after 882µs: ... read udp ...->10.0.0.2:53: read: operation would block
    GET https://www.amazon.com/ -> ERROR after 1.249ms: ... read udp ...->10.0.0.2:53: read: operation would block
    FAIL(httpsget): no verified 2xx HTTPS GET completed
    __EXIT_A__=1

### (c) serverload (TCP loopback, no DNS) — BEFORE the fix
    server listening on 127.0.0.1:46527
    serverload: goroutines=20 reqs/goroutine=10 total=200
    result: ok=0 fail=200 elapsed=12.014ms (16647 req/s)
    first-error: Get "http://127.0.0.1:46527/echo?id=19-0": dial tcp 127.0.0.1:46527: connect: operation now in progress
    FAIL(serverload): not all requests succeeded
    __EXIT_C__=1

Both errors are the *non-ready* return of a non-blocking socket surfacing as a
terminal error instead of the runtime parking on the netpoller and retrying:
  - UDP DNS read -> EWOULDBLOCK ("operation would block"), returned <2 ms.
  - TCP connect  -> EINPROGRESS ("operation now in progress"), all 200 in 12 ms.
Neither ever waited. That is exactly what happens when internal/poll's
`err == syscall.EAGAIN` / `err == syscall.EINPROGRESS` guards evaluate false:
the EAGAIN/EWOULDBLOCK path that calls `pd.waitRead`, and the EINPROGRESS path
that calls `pd.waitWrite`, are both skipped, so the raw errno is returned.

### Root cause — one instruction in the arm64 libroot dispatcher

`src/runtime/sys_haiku_arm64.s`, `asmsysvicall6`, errno readback:

    -   MOVW    (R2), R2          // signed 32-bit load: SIGN-extends
    +   MOVWU   (R2), R2          // unsigned 32-bit load: zero-extends

Haiku's POSIX errno values are B_GENERAL_ERROR_BASE-relative — bit 31 is set
(e.g. EAGAIN/EWOULDBLOCK = -0x7ffffff5, EINPROGRESS = -0x7fff8fdc). The syscall
package's constants are masked to 32 bits: `EAGAIN = Errno(-0x7ffffff5 &
0xffffffff)` = 0x0000_0000_8000_000b. A *signed* `MOVW` load of errno
sign-extends to 0xffff_ffff_8000_000b, so `err == syscall.EAGAIN` (a full
uintptr compare) is always false. Every non-blocking readiness check in
internal/poll therefore fails.

Why it stayed hidden through M1: `Errno.Error()` re-masks for haiku
(`n = n & 0x7fffffff + 1`), so error *strings* print correctly regardless of
the sign extension — which is why the transcript shows the right names. And M1's
tests (hello/fmt/chans/syscalls/sigtest) never do non-blocking network I/O, so
they never hit an `== syscall.Exxx` errno comparison. The amd64 Haiku port loads
errno with `MOVL`, which zero-extends on x86-64 for free; the arm64 translation
rendered it as the sign-extending `MOVW` instead of `MOVWU`.

Fix: patches/0002-haiku-arm64-M2-errno-zero-extend.patch (one instruction).

     completed a real TLS 1.3 handshake (cipher 0x1301 = TLS_AES_128_GCM_SHA256),

     Also proves the pure-Go DNS resolver over UDP now works.
 (b) 50 goroutines x 4 = 200 simultaneous external HTTPS connections, all 2xx,
     no hang — the poll(2) netpoll readiness path (arm the fd, park the
     goroutine, wake on readiness) under real concurrency with TLS.
 (c) In-process http.Server + 100 client goroutines x 20 = 2000 requests, each
     body a per-request SHA-256 the client verifies, all correct, no hang —
     accept/read/write readiness with no external dependency (deterministic).

from 0/200 to 200/200, (a) from DNS-fail to a verified 200. Same binary shape,
