M8 -- NATIVE Go toolchain distribution for DeBeOS (Haiku) arm64 (issue #378)
============================================================================
Goal: a Go toolchain whose binaries (go, compile, asm, link, cover, vet, cgo,
...) are haiku/arm64-native, so `go build` runs ON the box, not just
GOOS=haiku cross-compiles from Linux. Self-hosting acceptance = a native
`go build` of a hello program (spawning compile+link via the M6 fork+exec
path) that produces a runnable AArch64 Haiku ELF, PLUS a real dependency graph.

All merged M0-M6 fork work reused; NO new fork patch needed for the
distribution. Native tools rebuilt from the patched tree so the native `go`
carries patch 0004 (M6 pipe/fork+exec fix) -- the exact path `go build` uses.

== 1. Cross-build the native toolchain (Linux host) ==============================
From /local/home/benfelip/go-m0/korli-go (korli/go @ go1.26.1-haiku1 + patches
0001-0004 applied), host bin/go = go1.26.1 linux/amd64:

  GOROOT=$PWD GOCACHE=/tmp/... GOOS=haiku GOARCH=arm64 CGO_ENABLED=0 \
    GOTOOLCHAIN=local GOFLAGS=-mod=mod  ./bin/go install std cmd    -> exit 0

Produced (all AArch64 Haiku ELF, interp /system/runtime_loader, NEEDED libroot.so):
  bin/haiku_arm64/{go,gofmt}
  pkg/tool/haiku_arm64/{addr2line asm buildid cgo compile covdata cover dist
    distpack fix link nm objdump pack pprof preprofile test2json trace vet}  (19)
  $ file bin/haiku_arm64/go
    ELF 64-bit LSB executable, ARM aarch64, ... interpreter /system/runtime_loader
  $ file pkg/tool/haiku_arm64/*  ->  19/19 "ARM aarch64"

== 2. Assemble a self-contained GOROOT + hpkg ===================================
stage-goroot.sh assembled a packagefs layout (root -> /boot/system;
GOROOT=/boot/system/develop/lib/go): native go+gofmt at GOROOT/bin, native
tools at pkg/tool/haiku_arm64, pkg/include, std src, lib, go.env, VERSION,
LICENSE; relative symlinks bin/go -> ../develop/lib/go/bin/go; a
data/profile.d/go.sh; .PackageInfo. GOROOT is 328 MiB. (pkg/haiku_arm64 is
intentionally empty -- modern Go compiles std on demand into GOCACHE, so
`go build` on the box exercises the native compile+link, not prebuilt .a.)

hrev59996), build-hpkg-golang.sh:

== 4. BONUS -- real external dependency graph (debeos-aws) ======================
Native `go build` of graviton/go-arm64/debeos-aws (aws-sdk-go-v2: config,
feature/s3/manager, service/s3, service/cloudfront) ON the box. The box's NAT
egress reaches proxy.golang.org, so native `go mod` fetched the whole graph
over pure-Go TLS -- no vendoring, no Linux peer:

  $ go -C debeos-aws mod tidy
    go: downloading github.com/aws/aws-sdk-go-v2/config v1.28.6
    go: downloading github.com/aws/aws-sdk-go-v2/feature/s3/manager v1.17.41
    go: downloading github.com/aws/aws-sdk-go-v2/service/s3 v1.71.0
    go: downloading github.com/aws/aws-sdk-go-v2/service/cloudfront v1.44.1
    ... (transitive deps) ...                          tidy-exit=0
  $ go -C debeos-aws build -trimpath -ldflags=-s -o debeos-aws .   -> build-exit=0
  $ od -An -tx1 -N20 debeos-aws  -> ... 02 00 b7 00   (AArch64 Haiku ELF)
  $ ./debeos-aws s3 ls s3://haiku-graviton-hpkg-668984504585/staging/go-arm64/
    2026-09-19 01:40:14  121872113 staging/go-arm64/golang-1.26.1-1-arm64.hpkg
  (the natively-built AWS client hit S3 via the instance role over IMDS +
   pure-Go TLS -- a functioning real program built entirely by the native go.)

Note: the committed debeos-aws go.sum was incomplete (missing SDK entries);
`go mod tidy` completed it on the box. That is repo hygiene, not a toolchain
gap -- the fix is to commit the tidied go.sum.
