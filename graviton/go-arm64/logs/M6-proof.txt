ROOT CAUSE (precise)
====================
NOT the shared exec_libc.go child path, and NOT the forkx/asmcgocall/asmsysvicall6
trampolines (those are faithful to amd64 and were already exercised by M1/M2).

The fault is in runtime.pipe1 (src/runtime/sys_haiku_arm64.s), reached only via
syscall.forkExec -> forkExecPipe -> syscall.Pipe -> runtime.syscall_pipe. This
path was never exercised until fork+exec (M1/M2 never called pipe()), so the bug
was latent.

pipe1 is a straight translation of the amd64 shim. It uses 0(RSP)/4(RSP) as the
pipe(int fds[2]) output buffer:

    TEXT runtime·pipe1(SB),NOSPLIT,$16
        MOVD  RSP, R0        // &fds[0]  ==  0(RSP)
        MOVD  $libc_pipe(SB), R1
        BL    (R1)           // pipe() writes fds[0],fds[1] to 0(RSP),4(RSP)
        MOVW  0(RSP), R0      // fds[0]
        MOVW  4(RSP), R1      // fds[1]
        RET

But on arm64 the Go assembler prologue for a stack-frame'd non-leaf spills the
return address into the frame at 0(RSP):

        MOVD.W R30, -32(RSP)  // SP -= 32; store LR at 0(RSP)   <-- saved LR
        ...
        MOVD.P 32(RSP), R30   // reload LR from 0(RSP); RET to it

So pipe() overwrites the saved LR with fds[0] (a small integer, e.g. 3). The
epilogue reloads that clobbered word into LR and RETs to it — a jump to ~0x3 —
which faults: SIGSEGV via syscall.ForkExec, SIGBUS via os/exec (different low
address / alignment, same defect). This is why NO Go traceback printed: the
fault is a corrupted return, not a normal panic, and it recurs while the runtime
tries to unwind.

On amd64 the same shim is safe: there the return address sits ABOVE SP (pushed by
CALL), and the shim explicitly `SUBQ $16, SP` to reserve scratch below it, so its
0(SP)/4(SP) never collide with the return address. The arm64 translation did not
account for LR being spilled into the frame — arm64-specific by construction.

Localisation method: breadcrumb bisection. Raw byte-writes to fd 2 inserted in
syscall.forkExec and syscall.forkAndExecInChild showed 'a' (forkExec entry) and
'b' (after acquireForkLock) print, but 'c' (after forkExecPipe) never does — the
process dies inside pipe(). Disassembly of runtime.pipe1.abi0 then showed the
0(RSP) LR/buffer aliasing above.

THE FIX (patches/0004-haiku-arm64-M6-pipe-forkexec.patch)
=========================================================
Rewrite runtime.syscall_pipe (src/runtime/syscall_haiku.go) to call libroot
pipe(2) through the generic asmsysvicall6 dispatcher with a Go-managed buffer,
exactly as syscall_dup2 / syscall_close already do — instead of going through
the fragile runtime.pipe1 assembly shim:

    var fds [2]int32
    fdsp := uintptr(unsafe.Pointer(&fds[0]))
    call := libcall{fn: uintptr(unsafe.Pointer(&libc_pipe)), n: 1,
                    args: uintptr(unsafe.Pointer(&fdsp))}
    entersyscallblock(); asmcgocall(&asmsysvicall6x, &call); exitsyscall()
    if int(call.r1) == -1 { return 0, 0, call.err }
    return uintptr(fds[0]), uintptr(fds[1]), 0

asmsysvicall6 manages its own frame correctly (proven by every other libroot
call in M1/M2), so there is no LR/buffer aliasing. This is the arch-neutral form
(cf. os2_aix.go's pipe via syscall1(&libc_pipe,...)). runtime.pipe1/pipe1x are
left in place but become dead; a follow-up may remove them or fix the shim's
frame directly. One-file change; no toolchain-wide rebuild needed (gc rebuilds
the target runtime package on demand).

DEPLOYMENT NOTE (not a toolchain bug)
=====================================
The agent must be launched with a PATH that includes Haiku's shell directory
(/boot/system/bin; /bin/sh is a symlink to bash there). The runShellScript plugin
runs `sh` via exec.LookPath against the process environment; launched with a PATH
that omits the shell dir, the (now-working) fork+exec of ssm-document-worker
reaches execve and returns a clean `exec: "sh": executable file not found in
$PATH` — a diagnostic that itself confirms fork+exec is healthy, not crashing.
Launching the core with PATH=/boot/system/bin:/bin:... resolves it; Run Command
then returns Success. A launch job / appconfig that pins PATH is the durable fix.
